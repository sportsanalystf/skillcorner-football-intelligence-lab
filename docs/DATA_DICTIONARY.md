### Pitch dimensions

Pitch size is **not** constant, which matters for any cross-match comparison:

|   pitch_length |   pitch_width |   matches |
|---------------:|--------------:|----------:|
|            104 |            68 |         4 |
|            105 |            68 |        10 |
|            106 |            68 |         6 |

Every table in `data/processed/` therefore carries coordinates rescaled to a
standard 105 x 68 pitch alongside the native ones.

## 2. Identifiers and how the sources join

| id | where it lives | notes |
|---|---|---|
| `match_id` | directory name, `matches.json`, every file | integer, stable |
| `player_id` | `{id}_match.json` -> `players[].id`; tracking `player_data[].player_id`; events `player_id` | **the join key**; the tracking file uses this, not `trackable_object` |
| `trackable_object` | `players[].trackable_object`, `ball.trackable_object` | SkillCorner's internal object id; not used by any file in this repo |
| `team_id` | `home_team.id` / `away_team.id`, events `team_id` | |
| `event_id` | events CSV | string `"{event_type_id}_{n}"`, **unique within a match only**. The processed table adds `event_uid = "{match_id}:{event_id}"` |
| `phase_index` | events `phase_index`, phases `index` | joins an event to its phase of play |
| `frame` | tracking; events `frame_start`/`frame_end`; phases `frame_start`/`frame_end` | 10 fps video frame, shared across all three |

Verified on the reference match: every `player_id` appearing in the tracking
file exists in `1874553_match.json`; 4 named squad members are never
tracked (unused substitutes).

### The match clock

`timestamp` in the tracking file is a period clock, and both event and phase
files agree with it. The relationship, checked to floating-point equality:

```
period 1:  match_clock_s = (frame - period_1_start_frame) / 10
period 2:  match_clock_s = 2700 + (frame - period_2_start_frame) / 10
```

with `period_N_start_frame` from `match_periods[]` in the match JSON
(`{1: 10, 2: 29000}` for the reference match). `match_clock_s` is added
to every processed table and is the recommended join key for anything
time-based.

## 3. Coordinate systems

### 3.1 Tracking

Metres, origin at the centre spot, x along the long axis, y along the short
axis, exactly as the SkillCorner README states. Orientation is the broadcast
orientation and **changes at half time**. `home_team_side` in the match JSON is
a list indexed by period: `['left_to_right', 'right_to_left']` for the reference
match means the home team attacks towards +x in period 1 and towards -x in
period 2.

### 3.2 Dynamic events and phases of play — already attack-normalised

This is the single most important thing to get right and it is not stated in
the README. **The x/y columns on every dynamic-event and phase-of-play row are
expressed in the attacking frame of that row's own team**, not in broadcast
orientation.

Evidence (reproduced in `tests/test_event_orientation.py`): join every
`player_possession` row to the tracked position of its own player at
`frame_start`. For rows whose team attacks towards +x in that period the two
agree to 5e-7 m. For rows whose team attacks towards -x they agree only after
negating both coordinates — the raw difference is a median of 57 m, i.e. the
mirror image. The same holds for `passing_option`, `on_ball_engagement`,
`off_ball_run` and for the phases file.

The processed tables therefore expose four suffixes:

| suffix | frame | pitch | use for |
|---|---|---|---|
| *(none)* | attacking | native match metres | the raw value as delivered |
| `_att` | attacking | standard 105 x 68 | all tactical analysis |
| `_std` | broadcast | standard 105 x 68 | overlaying on `x_std`/`y_std` tracking |
| `_trk` | broadcast | native match metres | joining directly to tracking `x`/`y` |

`attack_sign` (+1 / -1) is stored on every row and is what converts between
the attacking and broadcast frames.


* `player_data` is either empty or holds exactly 22 players — there are no
  partial frames in this dataset. 16,057 of
  60,301 frames (27%) carry nothing at all:
  replays, crowd shots and stoppages.
* `is_detected` is `false` for 42% of player-frames in the
  reference match. Those positions are SkillCorner extrapolations, not
  observations.
* `ball_data.z` ranges -0.36 to 12.15 m. Small negative
  values are reconstruction noise.
* `possession.group` is `home team` / `away team` / null;
  `possession.player_id` is populated on only
  19% of frames.
* `image_corners_projection` is the quadrilateral of pitch currently visible in
  the broadcast. The processed ball table turns it into `visible_area_m2`,
  which is a good proxy for how much of the frame is extrapolated.

## 8. 3D body pose — `data/raw/bodypose/`

Two matches (1925299, 1996435) have pose. The full archives are ~600 MB
zipped / 3.3 GB of JSON each and are hosted on the Hugging Face Hub, not in
the repository. See `docs/LIMITATIONS.md` for what this project could and
could not download.

The committed sample, `sample_1925299_phase406.jsonl.gz`, is one phase of play:

{
  "file": "sample_1925299_phase406.jsonl.gz",
  "match_id": 1925299,
  "phase_index": 406,
  "tracking_frame_start": 49795,
  "tracking_frame_end": 49918,
  "pose_frames": 309,
  "joint_observations": 143637
}

Record structure mirrors the tracking file, with a `joints` dict added to each
player. 29 joints, each `{"xyz": [x, y, z], "p90_mae_cm": <error radius>}`.
Pose runs at **25 fps** against tracking's 10 fps: `pose_frame = 2.5 *
tracking_frame`, so only even tracking frames land exactly on a pose frame.

Joints: `nose`, `neck`, `lEye`, `rEye`, `lEar`, `rEar`, `lShoulder`,
`rShoulder`, `lElbow`, `rElbow`, `lWrist`, `rWrist`, `lThumb`, `rThumb`,
`lPinky`, `rPinky`, `midHip`, `lHip`, `rHip`, `lKnee`, `rKnee`, `lAnkle`,
`rAnkle`, `lHeel`, `rHeel`, `lBigToe`, `rBigToe`, `lSmallToe`, `rSmallToe`.

`z` is documented by SkillCorner as accurate *relative to the player's
centroid* and not in the pitch coordinate frame. It is therefore treated as
pose geometry here, never as height above the grass.

## 8b. Source quirks found while building this project

Each of these is measured by the code, asserted in `tests/`, and repeated in
`docs/LIMITATIONS.md`. None of them is documented upstream.

| quirk | scale | where it is handled |
|---|---|---|
| Event and phase x/y are in the **attacking** frame, tracking is in the broadcast frame | every row of both files | `src/preprocessing/build_events.py`, `tests/test_clock_and_orientation.py` |
| `event_id` is unique per match only | all 94,517 events | `event_uid` added in the processed table |
| **EPV, pressure and reception difficulty are entirely absent from 4 of 20 matches** (1886347, 1899585, 1925299, 2017461) | 3,829 of 18,792 possessions (20%) | reported on the app's Possession page; `tests/test_pipeline.py` |
| `xthreat` / `xpass_completion` are populated on `passing_option` and `off_ball_run` rows, never on `player_possession`; the possession equivalents are `player_targeted_xthreat` / `player_targeted_xpass_completion` | 48,431 vs 18,792 rows | `POSSESSION_KEEP` in `src/events/possessions.py` |
| `on_ball_engagement` rows carry a `time_start` up to ~4 s ahead of their own `frame_start` | 310 of 4,915 rows in the reference match | the project always joins on `frame_start`, which tracking agrees with exactly |
| One event player is absent from the match team sheet (player 973077, match 1953632) | 35 event rows in 94,517 | `tests/test_pipeline.py` bounds it |
| Pitch length varies 104-106 m | 20 matches | every table carries standard-pitch coordinates |
| The repository README says 10 matches; it ships 20 | -- | all 20 are used |
